# M1 design and security decisions

Scope: editable, resumable coach/team inputs, season/calendar constraints, optional aliases and assessment source reports. No generated assessments, plans or practices.

Browser forms cross into Next Server Actions, then strict bounded Zod schemas, authenticated repository transactions and tenant-scoped PostgreSQL. Existing managed authentication, revocable cookies, same-origin mutation protection and verified database TLS remain. No new dependencies, outbound services, uploads or model calls.

Store profile/assessment statements as field-level relational reports with actor, timestamp, Known/Unknown and context revision. Known means coach-reported, not independently verified. Empty/not-sure values are Unknown; no inference. Preserve report revisions. Calendar, phases and roster use relational columns with tenant-safe foreign keys. Only one workspace is exposed; account row lock serializes initial creation. Existing M0 seed workspaces are editable.

Save a bounded full setup draft atomically, compare context version to reject stale tabs, increment version and persist reports. Incomplete drafts may omit season dates; supplied dates/durations must always be valid. Completion additionally requires dates, resources and approved phase coverage. Calendar rows and roster IDs are verified against the selected season, never trusted for ownership. Repeated saves with an old version fail safely. Row policies cover every added tenant table.

Deletion in M1 is a synthetic verification repository operation, not a general privacy-deletion UI. Only migration-marked synthetic programs may be deleted, with session age under ten minutes and exact program-name confirmation. Hard database cascades purge all current tenant rows and source revisions in one transaction; revoke the actor's app sessions. Provider sessions are already revoked before app-session issuance in M0. There are no external content copies or live generation workers in M1. Backup erasure and deletion replay remain M7/pre-pilot gates; synthetic live deletion is not a complete production privacy claim.

Classification: aliases/account IDs are identifiers; profile and assessment text is user content; source timestamps/actors are attribution. Keep while program exists; all source revisions cascade on program deletion. No request bodies or aliases in logs; no secondary caches or analytics. Existing Supabase vendor-managed disk encryption is the synthetic-development assumption; actual production key ownership, rotation, backup controls and retention remain blocked by M0 pilot gates. Development secrets remain ignored locally; production secret manager is required before launch.

Threat review: forged owner/actor fields are excluded from strict schemas; ownership is resolved from session and protected by RLS. Foreign/stale row IDs are rejected. Malicious text is escaped by React and never executed or fetched. Flooding is bounded by payload/array/text limits and one workspace per initial flow; per-owner serialization prevents duplicate workspace races. Conflicting tabs fail with reload guidance rather than overwriting. Deletion abuse is bounded by synthetic marker, ownership, fresh login and confirmation. Database compromise remains a pilot operational risk, not solved by application logic. False coach reports remain attributed reports. No agent or model has privileges.

Verify: server-invalid dates/durations, Unknown persistence, reload/resume, two-coach isolation on every new table, stale writes, stable roster identity, synthetic deletion cascade and unaffected other tenant; desktop/mobile browser fixture with first-year 13U coach, nine unnamed players, twelve weeks, two 90-minute sessions and one hoop. Run structured Rafter review and standard remote scan before completion.
