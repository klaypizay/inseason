# M0 design review

Scope: a new Next.js modular monolith, managed Supabase password sign-in for provisioned adult coaches, a private PostgreSQL schema, revocable application sessions, and fixture-only AI. Onboarding and live generation wait for M1/M2.

Security design (Rafter auth, storage, API, ingestion, dependencies, deployment and STRIDE walks):

- Browser → Next.js → Supabase Auth verifies passwords. No password storage, custom JWT validation, public signup, OAuth, service identities or model tools. Adult status is self-attested, not age verification. Operators provision accounts and use provider MFA.
- After managed authentication, revoke the temporary provider session immediately; issue an independent 256-bit opaque application session. Only its SHA-256 digest is stored. This avoids retaining refresh/access tokens and makes logout independent of provider JWT expiry. Each repository transaction checks server-side revocation, 24-hour idle and seven-day absolute expiry. Password reset does not automatically revoke these independent sessions; operators must revoke app sessions too. A provider webhook is a pre-pilot follow-up.
- Runtime uses a dedicated non-owner, non-superuser, non-BYPASSRLS PostgreSQL role. Migration credentials never enter application paths. Private schema has no browser/Data API grants. Application derives actor from the session table, then sets transaction-local RLS identity. Program ownership checks, RLS and composite tenant foreign keys enforce isolation. A compromised application/DB credential remains a trust boundary, not something RLS can fix.
- Forms use Next.js Server Actions with same-origin protection, a 16 KB body cap, bounded Zod validation and escaped React output. Login attempts are limited in PostgreSQL by hashed normalized email plus a global ceiling; trusted-edge per-IP controls and provider abuse limits are required before pilot. No arbitrary outbound URLs, uploads, raw HTML or dynamic SQL from user values.
- Credential cookies are HttpOnly, SameSite=Lax, Secure in production, host-only. Pages are dynamic. Logout deletes the server session before deleting the cookie. Missing/foreign IDs have the same result. Errors never echo provider/SQL details.
- Coach IDs are identifiers; team/player aliases are content; run metadata is derived metadata. Synthetic data only. Retention/deletion launch requirements remain as documented in DATA_MODEL; M0 does not pretend to implement M7 privacy workflows. No prompt or credential logging. No secondary stores.
- Dependencies come from official npm packages, exact versions and lockfile, install scripts disabled. CI runs formatting, lint, typecheck, SQL isolation tests, fixture tests and build. Real Supabase/browser integration is separately verified when credentials exist.
- Deployment is not in scope. Before pilot: choose host/region, managed secret store, TLS ingress, database certificate verification, encrypted independent backups (30 days), operator key rotation and revocation runbook, external metadata-only audit retention, edge rate limits, coaching/privacy review and Rafter scan. Local DB TLS exemption is explicit and restricted to loopback.

STRIDE: spoofing → managed login + opaque sessions; tampering → strict forms/parameterized queries/tenant FKs; repudiation → attributed timestamps (full audit later); disclosure → private schema/RLS/generic errors; denial of service → bounded bodies/query limits/login quotas; privilege escalation → no owner mass assignment, no privileged runtime connection. Negative tests exercise foreign direct/nested IDs, mutation and generation status, session expiry/replay and cross-tenant relationships.

References checked: https://nextjs.org/docs/app/getting-started/installation ; https://supabase.com/docs/reference/javascript/auth-getuser ; https://supabase.com/docs/guides/auth/signout . Supabase access JWTs can survive logout; the application never uses them as database credentials.
