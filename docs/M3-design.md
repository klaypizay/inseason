# M3 design and security decisions

Scope: review/edit/save/accept roadmap versions, goal and weekly-content locks, phase/week navigation, scheduled session calendar, calendar preview, and recovery as a new version. Detailed weekly objectives, practice blocks and completion/check-ins remain M4–M6. No new paid AI calls or dependencies are needed.

Browser -> authenticated Server Actions -> owner-scoped repository -> private PostgreSQL. Existing revocable sessions and verified TLS remain the primitives; no new identities, tokens, service privileges or outward endpoints. IDs and bounded text are untrusted, validated with strict Zod schemas and escaped by React. All SQL values are bound. Every action resolves ownership from the session. Tenant/season composite keys plus forced RLS protect both immutable versions and relational calendar projections.

Each save creates an immutable schema-versioned snapshot, attributed to its coach, with base accepted revision, base context version, request ID and reason. Seasons hold current accepted and latest review pointers. Actor advisory lock plus season row lock serialize saves/acceptance with setup and generation; stale review/base/context fails. Duplicate requests return their existing result. Acceptance writes relational goals/weeks/sessions, an immutable accepted snapshot and current pointer atomically. No runtime update/delete grant on history. Synthetic program deletion cascades through all new records. Recovery copies teaching content into a new review against today's calendar; it never restores events or erases intervening history.

Locks protect goal text/checks and weekly emphasis/checkpoints; unlock must first be saved without altering protected text. New generations cannot replace locked content. Past weeks and past/completed/canceled sessions remain immutable. Session content IDs and content versions survive date-only moves. Team-local today's date comes from the server, never the browser. Initial acceptance expands availability deterministically and skips blocking events; a plain twelve-week, twice-weekly fixture yields 24 sessions. Sessions here are calendar slots, not generated practice plans.

Calendar preview works on a copy: shift eligible future dates by the start-date delta or keep them. Fixed events remain unchanged unless individually edited. Out-of-range teaching weeks require explicit reassignment/removal; missing range coverage can add clearly labeled empty teaching weeks. Conflicting future sessions require rescheduling or cancellation; cancellation retains the row and history. Completed/past sessions cannot be moved, canceled or deleted. Explicit coach overrides allow a rescheduled slot outside regular availability but never on blocking events. Phase boundaries remain coach-reviewable and must cover the chosen range. Preview is saved as an immutable draft; acceptance revalidates versions, current local date and all conflicts, preventing tampered/stale previews.

Classification: teaching content and snapshots are private user/derived content; IDs/actor attribution are identifiers; timestamps/reasons/request IDs are audit metadata. Same deletion and pre-pilot retention/backup policies as M0–M2, no new external copies or logs of bodies. The current verified Supabase storage/TLS configuration is retained; production KMS, rotation and independent backups remain the documented launch gates.

STRIDE: spoofed/foreign IDs fail session/owner/RLS checks; tampered locks/dates/statuses fail server comparison; immutable attributed revisions prevent ordinary app rewriting history; generic errors avoid data disclosure; bounded snapshots, at most 120 weeks/1500 slots, and 60 writes per ten minutes limit exhaustion; no privileged connection enters request paths. Abuse twins: replay accept -> idempotent; stale tab -> version conflict; recover history -> new draft with current constraints; malicious calendar preview -> server invariant validation; remove program -> authorized synthetic cascade. A compromised runtime remains a residual risk; no new privilege is added beyond tenant-scoped planning writes. Coaching correctness and real youth data approval remain independent pilot gates.

Verification will cover two-owner reads/writes and foreign parent IDs, duplicate/concurrent acceptance, locked/past/completed preservation, 24-slot expansion and exception days, seven-day shift with fixed tournament conflicts, shortening without silent removal, keep-dates mode, recovery/history and browser refresh/manual editing without AI. Rafter web-app review, source secrets check and standard remote scan required before completion.
