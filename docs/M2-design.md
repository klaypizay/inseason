# M2 design and security review

Scope: assessment and coarse season roadmap drafts; no acceptance, active plans, weekly practice detail or autonomous changes. Existing M0 placeholders remain for future actions. M2 implements typed assessSeason and draftRoadmap adapters selected by server configuration, with a deterministic fixture provider and a live provider.

Browser → authenticated Server Action → owner-scoped repository → approved fixed provider endpoint → strict schema/evidence validation → owner-scoped draft persistence. User reports are delimited untrusted data, never system instructions. Models receive no tools, database credentials, actor identity, email or player names. Team-level context contains bounded reports, calendar and resources; roster participation is summarized. No provider endpoint can come from user input. API keys stay server-side.

Calendar subdivision is deterministic: inclusive local dates, configured week start, clipped phase boundaries, all configured phases retained and no added phases. A season that starts midweek or midyear works without synthesizing past dates. The provider supplies teaching content keyed to authorized phase IDs and deterministic week numbers; server validation rejects missing/duplicate/foreign IDs. The server supplies dates itself.

Known assessment reports are copied verbatim from attributed source rows, never generated by the model. Generated claims are Likely (requires authorized, nonempty evidence) or Unknown; recommendations and assumptions remain separately labeled. No player judgments or invented observations. Source IDs are validated against current tenant context. Prompt injection cannot change authorization, trigger tools or promote drafts.

Create a UUID run before the network call, bind idempotency key to action/season/context, record status/attempts/usage/latency/model/prompt/schema version without prompt bodies. Maximum two active runs per program and configurable daily quota (default 30); serialize quota decisions. Requests have finite input/output bounds, sixty-second call timeout, at most one transient retry and one malformed-schema repair, at most three total calls. Authentication/authorization, quota and evidence failures do not retry. Failed runs have safe error codes, existing drafts remain intact.

Release database transaction before waiting on a provider. After response, recheck live session, ownership and context version before committing a validated draft. Reject late results after settings changes, logout or deletion. Running leases expire so interrupted processes cannot consume slots forever. Status/read APIs remain tenant-scoped. No active plan is touched. Drafts have private addressable URLs and survive refresh.

JSON payloads are schema-versioned bounded generation artifacts, consistent with DATA_MODEL. New tenant rows use RLS and composite parent keys. Program deletion cascades through drafts and runs. Raw rejected output is never stored. Privacy deletion takes precedence over the persistence skill's general retain-every-generation advice: retain safe metadata for failures, not invalid or deleted sensitive content.

Residual risks: source-ID validation cannot prove every natural-language inference is true or good coaching. Explicit draft/inference labels, source display and independent coaching review remain required before pilot. Provider retention, operational backups and real youth data approval remain launch gates. Live synthetic calls require the user's provider/key and spending authorization. Fixture checks can proceed independently.

Verification: exact inclusive week coverage, clipped boundary weeks, skipped phases, midseason starts, foreign/missing evidence, malformed outputs, transient/repair retry ceilings, two-tenant reads/writes, stale generation, idempotency, quotas, persisted reload and retry UI, latency/token measurements using synthetic fixtures. Rafter code review plus standard remote scan required before completion.
